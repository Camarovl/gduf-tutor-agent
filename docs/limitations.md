# 未完成部分及原因

考核要求 README 覆盖「已验证的功能清单，以及已知的问题与未完成部分」，
本文件展开说明。功能清单见 [../README.md](../README.md) 第四节。

## 一、明确未做的（官方加分项）

### 1. RAG：结合教材/课件并给出引用出处 ❌ 未做

**原因**：属于加分项而非必做，且它需要额外的文档解析、切块、向量库运维三项工作。
在只剩 23 天、MVP 四条优先的前提下砍掉。

**若要做**：现有架构预留了位置 —— 只需新增 `app/rag.py`（chromadb + PDF 切块），
在 `qa.answer()` 拼上下文时把检索结果并入 `context_block`，prompt 结构不用改。
预计 1.5 人日。

### 2. 多轮追问与澄清 ❌ 未做

信息不全时系统会直接按已有信息作答，而不是反问"你指的是哪个函数？"。

**原因**：需要状态机管理"待澄清"轮次，复杂度高但演示效果不明显。
当前用「引导式四段结构」替代 —— 即使问题模糊，也会先给定义再给例子，用户能自然接上。

### 3. 可视化报表导出 ❌ 未做

掌握度只有页面图表，不能导出 PDF/Excel。技术上加两个按钮即可，优先级排最后。

## 二、做了但有局限的

### 4. 拍照识别准确率依赖模型能力 ⚠️

实测结论：**视觉模型的 OCR 质量差异远大于代码本身的影响**。
弱模型会把 `f(x)=x²-2x+3` 认成 `f(x)=x2-2x+3`，甚至漏读题干后半句。

**应对**：不追求全自动。官方原话是「识别结果允许用户确认或修正后再入库」，
所以②页设计了完整的可编辑确认表单 —— 识别错就手动改，改完照样正常入库和统计。
这条降级路径在 `intake.analyze_image()` 里也有兜底（识别失败返回 `degraded=True` 的空草稿）。

**已知残留**：图片旋转、手写潦草、多题混拍三种情况识别率明显下降，未做预处理。

### 5. M4 生成题目的质量不稳定 ⚠️

模型生成的题目偶有：选项重复、答案与解析矛盾、超出课程范围。

**应对**：三道防线
1. 优先从本地题库抽题（人工确认过，最可靠）
2. 必须通过 `make_practice_validator` 校验"可客观判定对错"才采用
3. 校验失败带原因重试，仍失败则退回题库现存的题

**已知残留**：校验器只能保证结构合法（答案在选项中、类型正确），
无法判断数学内容是否真的正确。极端情况下可能生成一道题干自相矛盾的题。
彻底解决需要符号计算引擎验算，成本超出本次考核范围。

### 6. 知识点树规模有限 ⚠️

当前 **21 个节点、两层结构**，覆盖高中数学主干（集合、函数、指对、三角、向量、数列、不等式、导数），
但不是全集 —— 立体几何、解析几何、概率统计尚未录入。

**扩充成本很低**：往 `data/knowledge_points.json` 加条目 → 重跑 `python seed_data.py` 即可，
代码零改动。之所以没一次填满，是因为每个节点的 `explain` 和 `common_mistakes` 需要人工把关质量，
宁可少而准。

### 7. 无多用户体系 ⚠️（刻意不做）

单用户本地应用，所有人共用一份 SQLite。

**理由**：加了登录就要处理鉴权、数据隔离、密码存储、会话管理 ——
全是与题目无关的工作量，而且会引入密钥管理的新风险。
团队内部 PLAN.md 也明确写了这条禁令："任何时候觉得要不要加个登录/用户系统 → 不要加"。

若要支持多人，最小改造是给三张表加 `user_id` 列并在查询处带上过滤条件。

## 三、工程层面的已知不足

### 8. 测试覆盖不均 ⚠️

`tests/offline_check.py` 有 33 项，覆盖数据完整性、三条关键 SQL 语义、
两种校验器的畸形输入、判分逻辑、配置缺失时的优雅降级。

**未覆盖**：
- LLM 调用的集成测试（需真实 API，会产生费用且结果不稳定，不适合放进自检脚本）
- Streamlit 界面交互测试（需要 `streamlit.testing.v1.AppTest`，投入产出比低）
- Docker 镜像构建验证（本机未装 Docker，构建流程依据官方文档编写但未经实机验证）

🔴 **第 3 条尤其需要在答辩前补做**：找一台装了 Docker 的机器实际 build 一次。

### 9. 调用日志只记 token 不记金额

`llm_log` 表记录了 prompt/completion tokens 和重试次数，但没有换算成钱。
因为各家供应商计价方式不同，硬编码单价容易过时。
答辩时可用「累计 X 次调用、输入 Y / 输出 Z tokens」表述，侧边栏已实时显示这组数字。

### 10. 提示词没有版本管理

`prompts.py` 里的文案随迭代修改，历史版本只存在于 git 提交记录中。
更规范的做法是把每次 prompt 变更与对应的评测结果一起记录，便于回答"为什么改成这样"。
目前靠 [issues.md](issues.md) 里的文字说明替代。
